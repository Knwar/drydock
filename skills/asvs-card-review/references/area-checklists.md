# Per-area checklists

What to look for in the diff, area by area. Each item is something you can confirm or refute by reading code. Cite findings by ASVS chapter name (and verified requirement ID when you have the document).

## Authentication

- Passwords hashed with a slow, salted password hashing function (Argon2id, scrypt, bcrypt, PBKDF2 with a high work factor); never plain hashes (MD5, SHA-*) or reversible encryption
- No maximum password length that truncates silently; long passwords and all printable characters accepted
- Credential checks compare in constant time and fail closed on empty or null values
- Login, reset and signup responses do not reveal whether an account exists
- Rate limiting or lockout on login, reset, OTP and MFA endpoints
- Reset and verification tokens: cryptographically random, single-use, short-lived, invalidated after a password change
- Changing password, email or MFA settings requires re-authentication
- MFA, if present, cannot be skipped by calling the next step directly
- API keys and service credentials are checked on every request, scoped, and revocable
- OAuth/OIDC: state and PKCE used, redirect URIs exact-matched, ID tokens validated (signature, issuer, audience, expiry, nonce)

## Session management

- Session identifiers generated by the framework or a CSPRNG, never derived from user data or time
- Session rotated on login and privilege change; old session invalidated
- Logout invalidates the session server-side, not only the cookie
- Idle and absolute timeouts set; "remember me" scoped and revocable
- Cookies: `Secure`, `HttpOnly`, appropriate `SameSite`; narrow `Path`/`Domain`; `__Host-` prefix where possible
- State-changing requests protected against CSRF (SameSite plus token or origin check where needed)
- Self-contained tokens (JWT etc.): algorithm pinned server-side ("none" and algorithm switching rejected), signature verified before any claim is used, `exp`/`nbf`/`aud`/`iss` checked, short lifetime, revocation strategy for logout
- Tokens not placed in URLs or logs

## Access control

- Every new route, handler, job or GraphQL resolver has an authorization check, enforced server-side
- Object-level checks: the record being read or changed belongs to (or is shared with) the caller; IDs from the request are never trusted alone
- Function-level checks: admin and privileged operations check role or permission, not just "is logged in"
- Multi-tenant data always filtered by tenant in the query, not after fetching
- Mass assignment blocked: request bodies cannot set fields like `role`, `owner_id`, `is_admin`, `tenant_id`, `price`
- Deny by default; missing permission data means no access
- Checks are not only in the UI (hidden buttons are not access control)
- Bulk and export endpoints apply the same checks per item

## Input validation and output encoding

- Untrusted input validated on the server against an allow-list (type, length, range, format); client-side validation is not relied on
- SQL built with parameterized queries or a safe query builder; no string concatenation or interpolation with input, including `ORDER BY` and table/column names
- No shell commands built from input; if unavoidable, argument arrays and no shell
- HTML output auto-escaped by the template engine; any raw/unsafe HTML insertion (`dangerouslySetInnerHTML`, `v-html`, `|safe`, `innerHTML`) gets sanitized input only
- Context-correct encoding for HTML attributes, JavaScript, CSS and URLs
- Redirects and forwards validated against an allow-list (no open redirects)
- Deserialization of untrusted data uses safe formats (JSON) and never native object deserializers (pickle, Java serialization, unsafe YAML loaders)
- Regexes on untrusted input are not vulnerable to catastrophic backtracking
- Business rules enforced server-side: quantities, prices, limits, state transitions, and sequence of steps cannot be skipped or replayed
- Server-side requests to URLs from input (webhooks, previews, imports) restricted to allowed hosts and schemes; internal and metadata addresses blocked

## Cryptography

- Well-known libraries and high-level APIs used; no home-made crypto
- Modern algorithms and modes: authenticated encryption (AES-GCM, ChaCha20-Poly1305); no ECB, no unauthenticated CBC; no MD5 or SHA-1 for security purposes
- Nonces and IVs never reused with the same key; generated as the library recommends
- Random values for tokens, IDs and keys come from a CSPRNG, not `Math.random`, `rand()` or similar
- Secret comparisons in constant time
- Keys not hard-coded; loaded from a secret store or environment; rotation possible
- Password hashing uses a password hashing function, not a fast hash or a KDF misused

## Secrets and configuration

- No secrets, tokens, private keys or connection strings in code, tests, fixtures, example configs, docs or commit history of this change
- Debug modes, verbose errors, admin consoles and test endpoints disabled in production config
- Security-relevant settings fail closed when missing or malformed (no `verify=false` defaults, no empty-string secrets accepted)
- CORS allow-list explicit; no wildcard origin with credentials; no reflected `Origin`
- Security headers set where the change affects responses: Content-Security-Policy, Strict-Transport-Security, X-Content-Type-Options, frame-ancestors / X-Frame-Options, Referrer-Policy
- TLS enforced for external connections; certificate verification not disabled
- Least privilege for new service accounts, database users, cloud roles and tokens

## Error handling and logging

- Errors returned to clients are generic; no stack traces, SQL, internal paths or versions
- Exceptions in security checks fail closed (an error in an auth check denies access)
- Security events logged: login success/failure, access denied, privilege changes, admin actions, token or key use where relevant
- Logs contain who, what, when, and outcome, but never passwords, tokens, session IDs, full card numbers or unnecessary personal data
- Log injection prevented (newlines and control characters in user input encoded)
- Errors are not swallowed silently around security operations

## Data protection

- Sensitive data identified for the change (personal, financial, health, credentials) and only the needed fields collected, returned and stored
- API responses do not over-return fields (full user objects, internal flags, hashes)
- Sensitive data not in URLs, query strings, client-side storage or analytics events
- Cache-Control set to prevent caching of sensitive responses
- Encryption at rest for sensitive stores where required; backups and exports covered too
- Retention and deletion honoured; deleted data actually removed or anonymised
- Data sent to third parties (analytics, LLMs, email providers) is intended and minimal

## File handling

- Upload size, count and type limits enforced server-side; type checked by content, not only extension or client MIME type
- Stored filenames generated server-side; user-supplied names never used as paths
- Path traversal blocked on every read or write that includes input (`../`, absolute paths, encoded variants); paths resolved and checked against the base directory
- Uploaded files stored outside the web root or served with a safe `Content-Type` and `Content-Disposition: attachment` where appropriate
- Archive extraction guards against zip slip and decompression bombs
- Images and documents from users processed with up-to-date libraries; no server-side execution of uploaded content
- Downloads check authorization for the specific file

## API and web service

- Each endpoint authenticates and authorizes (see above); webhooks verify signatures and reject replays
- HTTP methods restricted; state changes not possible via GET
- Request body size limits and pagination limits enforced
- Content type checked; JSON parsers reject unexpected types
- Rate limiting on expensive or sensitive endpoints
- GraphQL: depth and complexity limits, introspection disabled in production if not needed, authorization in resolvers not only at the gateway
- Error responses consistent and non-revealing; 401 vs 403 used correctly
- API keys and tokens accepted in headers, not query strings

## Dependencies and build

- New dependencies are necessary, maintained, widely used, and from the expected publisher (watch for typosquats)
- Versions pinned via lockfile; lockfile changes match the manifest changes
- No known-vulnerable versions introduced (check the dependency audit results)
- Install and build scripts of new packages reviewed if they run code on install
- CI and build changes do not expose secrets to untrusted code (forks, pull requests from outside)
